# 0.11.1 → 0.11.5 regression audit

Comparison: `63d141a` (0.11.1) → `b7a1887` (0.11.4), plus the 0.11.5 release candidate. Reviewed on 2026-09-10 JST.

## Confirmed regressions

1. **Duration disappeared for media above 16 MiB.** In 0.11.2, `APITranscriptionModal.createTimeRangeControls` gained a waveform memory guard inside the same block that discovers duration. The guard threw before reading/decoding the file, so the catch displayed Unknown and left the end time empty. It was inherited unchanged by 0.11.3. The limit is file size, not minutes.

   The identical synthetic 17 MiB MP4 passed against the 0.11.1 modal and failed against 0.11.3. Version 0.11.4 fixed the duration by reading metadata through `Vault.getResourcePath` independently of waveform decoding. Small files retain the original audio-decode fallback. Closing the modal cancels the metadata request; errors and invalid/infinite durations have a timeout and release the media resource.

2. **Version 0.11.4 removed the waveform and its direct range-selection interaction for files above 16 MiB or two hours.** Duration and numeric time fields remained available, but the modal skipped `Vault.readBinary` and waveform decoding. That was a functional reduction from 0.11.1 and was visible with the user's 56-minute file. The 0.11.5 candidate restores waveform decoding for those files, asks Web Audio for an 8 kHz preview, reduces the decoded audio to a canvas-sized amplitude envelope, and then releases the full `AudioBuffer`. Metadata still supplies duration independently if the preview cannot be decoded.

## Compatibility risks fixed since 0.11.1

1. **Legacy temporary-folder collisions:** External import now preserves unmarked folders, files and invalid markers and chooses `ai-transcriber-temp-managed` (then numbered alternatives) when the original path is occupied. Existing marked roots are reused. Cleanup discovers only matching top-level roots, requires ownership markers, and can recover alternate-root sessions after restart. A bare session ID matching multiple roots does not trigger deletion; cleanup by file identifies its exact root. Six integration tests cover import, restart cleanup, collisions, unknown-data preservation, copy failure and ambiguous IDs.

2. **Rate-limit recovery:** Both transcription clients now retry temporary HTTP 429 responses at most twice, with at most 60 seconds of automatic waiting per call. `Retry-After` seconds and HTTP dates are honored; otherwise exponential backoff with jitter applies. The same client carries the cooldown into subsequent chunks, including after retry exhaustion. A server delay exceeding the remaining budget surfaces the error rather than resending early. Quota/billing errors and unknown explicit error codes are not retried. HTTP 408/5xx, transport failures and local timeouts remain non-retryable for transcription because processing status is uncertain. No outer strategy retry was restored. Tests cover recovery, both header forms, limits, later chunks, cancellation and non-retryable outcomes.

The original risks were identified from the release diff; this does not imply that the user's vault or API session encountered them. The retry policy follows [OpenAI's rate-limit guidance](https://help.openai.com/en/articles/5955604-how-can-i-solve-429-too-many-requests-errors).

## Other changed paths checked

- Original-file fallback is restricted to eligible formats/size and no time range. New controller tests verify a range, cancellation or memory error never causes full-file upload; unsupported WMA/MOV/MKV are not directly uploaded.
- VAD-produced WAV is labeled as WAV, and a selected range is not applied twice. This is covered at the controller boundary and by real decoding tests for both routes.
- WMA embedding uses the generated worker and WASM in the browser tests; WMA v1/v2 decode and selected ranges are checked in both production decoder paths.
- Multi-channel downmix, WAV chunk parsing and transcription-path encoded/decoded budgets are covered by the existing suites. The 128 MiB / two-hour processing budget already existed in 0.11.1 for local transcription processing; it did not remove the modal waveform in 0.11.1.
- Resource disposal now uses the public cleanup contract; VAD cleanup failures are isolated. Modal close invalidates pending UI loads. Temporary-file cleanup requires ownership markers and preserves unknown files.
- Title API and CSS changes: removed `api-transcription-*` selectors have no references in current TypeScript. Actual modal classes use `ai-transcriber-*`. No file-save or API-key storage implementation was changed by these commits.
- The full transcription start screen is rendered in Chromium from both the exact 0.11.1 modal and the release candidate. Both expose the title, five model choices, selected file/type, estimate, language, output folder, post-processing, dictionary, related information, waveform, time-range fields, Cancel and Start transcription controls. Model changes still update the saved settings callback.
- Every advertised 0.11.1 audio/video extension plus WMA is exercised through both production decoding routes with generated real media. MP3, M4A, WAV, FLAC, OGG, AAC, MP4, M4V, MOV, MKV, WebM and WMA Standard v1/v2 decode a selected one-second range. A common AVI encoded as MPEG-4 video plus MP3 audio fails in the Chromium runtime in both routes; this is an inherited codec/runtime limitation, not a post-0.11.1 regression. The picker still accepts AVI, and the README already describes video support as codec- and environment-dependent.

## Validation and limits

See `docs/testing/media-duration-regression.md` for repeatable commands. Unit/controller tests use mocked external I/O; media tests use actual Chromium decoding with a small Obsidian host shim. Native Obsidian 1.13.7 on macOS was also checked with the built plugin in an isolated profile and disposable vault: a 17 MiB MP4 showed 0:03, MOV showed 0:03, the 13-minute MP4 showed 13:00, and the over-two-hour MP4 showed 2:00:03. The registered transcription command opened the real modal; enabling range selection populated and enabled the matching end-time fields. A real 56-minute M4A selected by the user was checked with the 0.11.5 candidate and retained its waveform. The dialogs were cancelled and the test app was closed. No paid end-to-end transcription or Windows native Obsidian run was performed during this audit.

Deleted 0.11.1/0.11.2 GitHub releases were not recreated.

Validation before the compatibility fixes: 321 tests / 64 suites, 22 real-media browser tests, zero dependency audit findings and four native Obsidian modal checks. See the final compatibility validation below for the updated build.

Version 0.11.4 compatibility validation: `npm run check:community` passed (345 tests / 65 suites), including both production client constructors and concurrent cooldown extension; `npm run test:media` passed all 22 then-current real-media cases.

Version 0.11.5 release-candidate validation: `npm run check:community` passed (345 tests / 65 suites); `npm run test:media` passed all 44 real-media/start-screen cases; and the exact 0.11.1 modal passed the same start-screen control-contract test. Full and production-only dependency audits reported zero vulnerabilities. No paid API request was sent.
